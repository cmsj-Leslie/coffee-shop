3 系统需求分析
本章针对基于 SpringBoot 的“咖啡商城”在线销售系统的设计与实现进行系统的需求分析。主要内容包括系统可行性分析、功能性需求分析以及非功能性需求分析等关键环节。其中，功能性需求分析梳理了系统的业务边界，涵盖了前台用户端的商品浏览、购物车与订单结算，以及后台管理端的商品维护、订单发货处理等核心模块。

3.1 可行性分析
3.1.1 技术可行性
本系统选择 SpringBoot 作为后端开发框架。利用其“约定优于配置”的特性，能够快速整合各类技术组件，显著降低了系统的配置复杂度，并提升了从初始化搭建到业务逻辑实现的开发效率。
技术的可行性可以从以下几方面来进行分析：
（1）生态系统方面： Java 体系提供了丰富的开源项目和解决方案，为开发过程中遇到的常规问题提供了基础的技术支持。
（2）开发效率方面：SpringBoot 集成了常用的第三方库（Starter 依赖），如 Web 开发、数据库连接模块等，能够让开发人员迅速搭建起基础的单体架构 Web 应用程序。
（3）功能实现方面：本系统采用了 MyBatis 作为持久层框架，配合 MySQL 数据库，能够稳定地处理电商系统的商品数据流转和订单状态变更。这套底层的技术组合在众多同类电商项目中已被广泛应用，技术路线成熟。
SpringBoot 框架通过集成核心功能，保障了项目的开发进度，对于“咖啡商城”这类基础电商系统而言，选用该技术栈是切实可行的。

3.1.2 经济可行性
本系统的开发成本主要包含个人的时间精力以及少量的硬件投入。由于开发过程中使用的 SpringBoot、MyBatis 框架以及 MySQL 数据库都是开源免费的，所以不需要支付额外的软件授权费用。硬件方面只需要使用现有的个人电脑即可完成开发。

3.1.3 操作可行性
“咖啡商城”系统采用的是标准的 B/S 架构，用户只需要通过普通的 Web 浏览器即可访问商城平台，不需要额外学习复杂的客户端操作逻辑。

在界面设计上，前台页面采用了直观的网格化商品展示和清晰的导航栏，用户可以按照常规的网购习惯完成加入购物车、填写收货地址和提交订单等一系列流程。

后台管理端同样采用了格式化的表单和侧边菜单，管理员能够方便地进行商品上下架和订单状态修改。这种符合普通用户直觉的交互设计，使得系统的操作学习成本极低，因此在操作上具备充分的现实可行性。

3.2 功能性需求分析
3.2.1 功能模块详细设计
“咖啡商城”是一个基于 SpringBoot 框架构建的单体电商系统。系统利用 MyBatis 框架与 MySQL 数据库进行数据交互，业务逻辑层处理核心的购物车计算与订单状态流转，并通过控制层（Controller）将处理结果传输至视图层，最终在前端页面上展示给用户。稳定的数据流转是支撑业务场景适配的核心要素。该架构设计保证了业务逻辑的清晰，便于后期的维护。系统整体的业务逻辑架构如图3-1所示。

图3-1 系统架构图

前台用户端模块详细设计：
（1）商品展示与搜索：用户可以浏览不同分类的咖啡豆及周边商品，支持根据关键字进行模糊搜索。首页需展示基于协同过滤算法推荐的商品列表，并通过良好的 Web 界面交互设计提升用户的转化效率[24]。
（2）购物车与结算：用户可以将心仪的商品加入购物车，并在结算页面勾选可用的优惠券。系统需在后台进行优惠券起步门槛的核验，并在提交订单时通过事务机制扣减库存。这一流程确保了后端状态流转的安全严密性。
（3）AI 智能咨询：系统前台提供一个聊天浮窗，调用大语言模型（如 DeepSeek）接口，允许用户通过自然语言询问咖啡风味或获取智能推荐建议。
（4）个人中心：用户可查看历史订单状态、管理收货地址、修改登录密码以及对已完成的订单进行评价。

后台管理员端模块详细设计：
（1）商品与分类维护：管理员可对商品分类进行增删改，发布新的咖啡商品，并上传商品图片至 OSS，控制商品的上架与下架状态。
（2）订单与发货处理：管理员可查看全站的订单列表，对已支付的订单进行物流单号录入并核销发货状态。
（3）评价管理：管理员可查阅用户的商品评价，必要时对违规的评论进行隐藏或删除处理。
（4）优惠券下发：管理员可配置不同类型的优惠券（如满减券、折扣券），设置有效期与最低消费门槛。

3.3 非功能性需求分析
为了保障商城在实际网络环境中能够平稳运行，除了基础的功能需求外，本系统还需满足以下几个方面的非功能性需求。

3.3.1 性能需求分析
系统在处理常规的页面加载和静态资源请求时，响应时间应控制在合理范围内。对于涉及订单生成、库存扣减等核心数据写入的接口，需保证数据库操作的执行效率，避免因复杂的联合查询导致请求阻塞。

3.3.2 安全性需求分析
安全性是电商系统的基础防线。用户的登录密码必须经过哈希加密后存入数据库，不能明文存储。在涉及金额计算和库存变更的环节，必须在后端业务逻辑层进行严格校验，杜绝依赖前端传递计算结果的漏洞。
此外，订单的生成过程需要加入 `@Transactional` 事务控制，确保在并发场景下不会出现库存超卖或数据脏读的现象，这也是各类应用系统化功能异常测试重点关注的理论设定边界[25]。

3.3.3 易用性需求分析
系统的前台界面排版应保持简洁、清晰，避免过多的冗余元素干扰用户的视线。购物车的加购提示、订单的支付流程应附带明确的反馈信息，确保不同年龄段的用户都能顺畅地完成购物操作，进而显著提升用户的留存率与购物体验。

3.3.4 可扩展性需求分析
本系统虽然采用了基础的单体架构，但在代码编写过程中尽量遵循了“高内聚，低耦合”的原则。系统将控制层、业务逻辑层和持久层进行分离，明确了各自的处理边界，减少了层与层之间的直接依赖。
这种设计方式为系统后续可能增加的新功能（例如接入微信支付或引入 Redis 缓存）预留了对应的接口代码，方便在不破坏原有逻辑的情况下进行功能扩充。
