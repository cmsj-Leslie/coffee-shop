4 系统详细设计

4.1 系统体系结构
咖啡商城是一个采用 B/S（Browser/Server，浏览器/服务器）架构的单体电子商务项目。本系统主要分为管理员和普通用户两个角色。其中，普通用户可以进行商城主页浏览、商品搜索、购物车管理、优惠券核销结算、订单支付模拟、AI 智能咨询以及商品评价等操作；管理员则可以实现数据看板分析、商品发布与上下架、分类管理、优惠券配置管理、订单发货处理、系统用户管理及评价数据审核等操作。本系统的总体功能结构如图4-1 所示。

图4-1 系统功能结构图

（1）登录流程设计：系统的用户登录功能涵盖了前台用户登录与后台管理员登录。用户在登录界面中输入邮箱和密码后，系统将输入的信息与数据库 user 表中对应的数据进行比对。信息匹配成功则创建 Session 并跳转至相应的主页或后台控制台。系统登录模块流程如图4-2 所示。

4.2 系统架构设计
本系统后端代码基于单体开发模式，采用了标准的三层架构，将代码划分为表示层、业务逻辑层和数据持久层。这种分层结构有助于代码的管理和后续的修改。

4.2.1 表示层设计
表示层主要负责与用户进行交互。系统前台使用 Thymeleaf 模板引擎来展示商品等动态数据。用户在页面上点击商品或加入购物车时，会向后端发送 HTTP 请求。控制层（Controller）接收到这些请求后，会先做一些基础的参数校验，然后把具体的处理任务交给业务逻辑层去完成。

4.2.2 业务逻辑层设计
业务逻辑层（Service 层）主要用来编写系统的核心业务代码。当接收到控制层的调用时，业务逻辑层会进行具体的计算和判断。例如，在处理用户提交订单的请求时，计算订单总价、判断优惠券是否可用以及检查商品库存等代码都在这一层实现。
另外，为了防止超卖，在执行写入订单、更新优惠券和扣减库存等一连串操作时，系统在方法上添加了 `@Transactional` 注解来控制事务。如果中途发生库存不足等错误，程序会触发事务回滚，从而保证数据库中数据的正确性。

4.2.3 数据持久层设计
数据持久层主要负责直接与 MySQL 数据库交互，执行数据的增删改查。系统使用了 MyBatis 框架，通过编写 Mapper 接口和对应的 XML 映射文件，把数据库表里的记录转换成 Java 实体类。这种方式让开发人员能够直接操作对象，避免了手动拼接复杂 SQL 语句可能带来的错误。

4.3 系统数据库设计
在进行数据库设计时，需要分析系统的各项业务需求，明确交易数据流程及数据映射关系。本系统确立了多个核心数据实体，包括用户、商品、订单、购物车和评价等。

4.3.1 数据库逻辑设计
数据库的逻辑设计主要是将商城中的实际业务对象抽象成数据模型。本系统通过 E-R 图来展示各个实体对象以及它们之间的联系。系统的整体 E-R 图如图4-7 所示。
