# 🎓 《咖啡商城在线销售系统》答辩必考 Q&A 与高分话术指南

这份指南从你项目中最具技术含量的 **AI、算法、并发锁** 三大维度出发，预判了答辩导师最喜欢问的“刁钻”问题，并为你定制了**“不夸大、不心虚、懂底层”**的满分应答话术。

---

## 💡 一、 关于 AI 智能咨询模块（最高频考点）

**💀 导师提问：**
*“现在调大模型 API 谁都会，你这个 AI 模块跟别人直接嵌套一个网页有什么区别？你怎么实现所谓的‘上下文记忆’的？”*

**✅ 绝杀回答：**
“老师您好，我的 AI 模块**并不是直接嵌套网页（iframe）**，而是纯后端对接了 DeepSeek 和 Gemini 的原生 API。为了实现‘上下文记忆’，我没有依赖前端缓存，而是在生成新的请求前，会**通过后端主动向数据库（或 Session）去查询该用户最近的 N 条聊天历史**，然后将历史问答拼接到本次的 prompt（提示词）中一同发送给大语言模型。这样既保证了对话的连贯性，也确保了用户的会话数据安全地保存在咱们自己的服务器上，而不是交给第三方前端。”

---

## 📈 二、 关于个性化推荐算法（核心亮点）

**💀 导师提问：**
*“你摘要里写了基于物品的协同过滤，这个算法的数据依据是什么？如果系统刚上线没有数据，你怎么推荐？”*

**✅ 绝杀回答：**
“为了避免数据冷启动的问题，我的推荐分为两部分。
在用户没有任何行为前，系统默认按**‘总销量’和‘最新上架’**来呈现数据（也就是全局热点排序）。
当用户开始产生**加购、收藏**等隐式行为后，我的基于物品的协同过滤（Item-based CF）算法才开始介入。它的基本依据是：系统会计算不同咖啡商品在用户加购列表中的‘共现频率’。如果两个商品经常被同一个用户买，那它们的相似度就高。当用户点击某款咖啡时，系统就会把相似度最高的几款一并推出来。受限于开发周期，目前的推荐维度还比较浅，未来的优化方向是在前端加入‘页面停留时长’埋点，让推荐基数更宽广。”

---

## 🔒 三、 关于购物车、订单防超卖（底层架构）

**💀 导师提问：**
*“你说你使用了 `@Transactional` 来控制事务防止超卖，但具体是怎么防止并发超卖的？为什么用数据库而没用 Redis？”*

**✅ 绝杀回答：**
“老师好，由于本系统定位于中小型垂直零售站，当前的并发量使用 MySQL 的底层锁完全可以覆盖。在结算时，我是依靠 `@Transactional` 结合带有悲观锁机制的 SQL 语句来防超卖的：即 `UPDATE stock = stock - num WHERE id = ? AND stock >= num`。
如果是并发请求来扣减同一个商品的库存，MySQL 底层会触发行级锁排队。如果某人执行该语句返回影响行数为 0（说明 `stock >= num` 的条件不满足了），我的业务层就会立刻抛出异常，此时 `@Transactional` 就会捕捉到并自动把刚才执行的步骤**全部回滚（撤销）**，从而绝对杜绝了‘库存变成负数’的情况发生。至于 Redis 分布式锁，那是我论文第七章提到的未来架构升级方向。”

---

## 🏗️ 四、 关于架构与前后端选型（避坑排雷）

**💀 导师提问：**
*“现在大家都用 Vue、React 做前后端分离，为何你还在使用 Thymeleaf 这种老前端模板？”*

**✅ 绝杀回答：**
“我在技术选型时其实考虑过前后端分离，但出于以下两点考量最终选择了单体 SpringBoot + Thymeleaf：
1. **符合电商业务诉求**：咖啡商城前台的核心是卖货，采用 Thymeleaf 服务端渲染（SSR），页面在服务器端就拼装好了，有利于商品页面的 **SEO（搜索引擎抓取）** 和首屏加载速度，这对电商拉新非常重要。
2. **架构收敛、降低运维成本**：目前全站功能都在一个工程里即可完成路由跳转和 Session 同步检查，维护成本极低，非常契合咱们这种中小型在线店铺的初期快速上线需求。”
